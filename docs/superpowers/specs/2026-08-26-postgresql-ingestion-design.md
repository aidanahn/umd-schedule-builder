# PostgreSQL Data Model and Ingestion Design

## Goal

Add a provider-agnostic PostgreSQL persistence layer for complete Testudo department snapshots. The database will expose normalized current course data for schedule building, retain immutable seat observations, and retain derived objective seat-change events for future watch processing.

The existing JSON snapshot command remains independent and unchanged.

## Scope

This phase includes:

- A local PostgreSQL 17 container for development.
- Drizzle ORM with the `node-postgres` driver.
- Versioned, reviewable SQL migrations.
- Normalized course, section, requirement, instructor, and meeting tables.
- Immutable department ingestion, seat observation, and seat event tables.
- Transactional and idempotent PostgreSQL ingestion.
- A separate `npm run ingest:db` command.
- Offline tests and opt-in PostgreSQL integration tests.

This phase does not include:

- Users, authentication, watches, or notification delivery.
- Schedule generation or a web API.
- A recurring scraper or worker.
- Historical backfills or out-of-order ingestion.
- Additional semesters or department discovery.

## Technology and Configuration

- `drizzle-orm` is the primary abstraction for schema definitions, queries, and transactions.
- `drizzle-kit` generates and applies SQL migrations.
- `pg` provides the underlying PostgreSQL connection pool.
- Application code receives the connection through `DATABASE_URL` only. It does not branch on Docker or database provider.
- `dotenv` loads local development configuration for CLI and migration commands.

The repository will include:

- `docker-compose.yml` with a PostgreSQL 17 Alpine service, named volume, and health check.
- `.env.example` with placeholder values for `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `POSTGRES_TEST_DB`, `POSTGRES_PORT`, `DATABASE_URL`, and `TEST_DATABASE_URL`.
- `.gitignore` coverage for `.env` and local environment variants while retaining `.env.example`.
- A PostgreSQL initialization script that creates the dedicated test database named by `POSTGRES_TEST_DB`. It uses container environment variables and contains no credentials.

Compose reads real values from the developer's uncommitted `.env`. Neither `docker-compose.yml` nor application source contains credentials.

## Database Model

Identifiers generated by the application use UUIDs from Node's cryptographic UUID generator. This avoids requiring a PostgreSQL extension and keeps the schema portable across PostgreSQL providers.

### Reference and ingestion state

#### `semesters`

- `code text primary key`, constrained to six digits.
- `created_at timestamptz not null default now()`.

#### `departments`

- `code text primary key`, constrained to four uppercase ASCII letters.
- `created_at timestamptz not null default now()`.

#### `department_ingestions`

- `id uuid primary key`, supplied by the application.
- `semester_code text not null` referencing `semesters`.
- `department_code text not null` referencing `departments`.
- `collected_at timestamptz not null`.
- `source_url text not null`.
- `status text not null`, constrained to `complete`.
- `summary jsonb not null`.
- `warnings jsonb not null`.
- `snapshot jsonb not null`, containing the exact parsed `DepartmentSnapshot` object.
- `created_at timestamptz not null default now()`.
- Unique constraint on `(semester_code, department_code, collected_at)`.

Only complete snapshots are persisted. The exact snapshot JSONB is the provenance record used to reproduce comparisons and diagnose normalization problems.

#### `department_ingestion_heads`

- Composite primary key `(semester_code, department_code)`.
- `latest_ingestion_id uuid null` referencing `department_ingestions`.
- `latest_collected_at timestamptz null`.
- `updated_at timestamptz not null default now()`.

The nullable initial state lets a transaction create and lock a head row before the first ingestion exists. Updating this row is the final successful-ingestion state change inside the transaction.

### Current normalized catalog

#### `courses`

- Composite primary key `(semester_code, course_id)`.
- `department_code text not null`.
- `title text not null`.
- `credits_min numeric not null` and `credits_max numeric not null`, with nonnegative and ordered checks.
- `grading_methods text[] not null`.
- `gen_ed_codes text[] not null`.
- `description text null`.
- `is_active boolean not null default true`.
- `last_seen_ingestion_id uuid not null`.
- Foreign keys to semester, department, and ingestion records.

Indexes support active courses by semester/department and direct course ID lookup.

#### `course_requirements`

- Composite primary key `(semester_code, course_id, position)`.
- `position integer not null`, preserving source order.
- `label text not null`.
- `text text not null`.
- Composite foreign key to `courses` with cascade deletion.

Requirements for a course are replaced inside the same transaction when that course is seen again.

#### `sections`

- Composite primary key `(semester_code, section_id)`.
- `course_id text not null`.
- `section_number text not null`.
- `delivery_mode text not null`, constrained to the parser's four values.
- `notes text[] not null`.
- `is_active boolean not null default true`.
- `last_seen_ingestion_id uuid not null`.
- Composite foreign key to the owning course and foreign key to the last-seen ingestion.

Indexes support active sections by course and direct section ID lookup.

#### `section_instructors`

- Composite primary key `(semester_code, section_id, position)`.
- `position integer not null`, preserving source order.
- `name text not null`.
- Composite foreign key to `sections` with cascade deletion.

Instructor names remain section-specific because Testudo provides no stable instructor identity.

#### `section_meetings`

- Composite primary key `(semester_code, section_id, position)`.
- `position integer not null`, preserving source order.
- `days text[] not null`.
- `start_minutes integer null` and `end_minutes integer null`.
- `display_time text null`.
- `building text null`, `room text null`, and `meeting_type text null`.
- Composite foreign key to `sections` with cascade deletion.
- Checks require both time boundaries to be null or both present, constrain minutes to a single day, and require the end to be at or after the start.

Meetings and instructors for a seen section are replaced transactionally. Records for inactive sections remain available for provenance but normal catalog queries filter on `sections.is_active`.

### Immutable seat history

#### `seat_observations`

- Composite primary key `(ingestion_id, semester_code, section_id)`.
- `course_id text not null`.
- `total_seats integer not null` and `open_seats integer not null`.
- `waitlist_count integer null` and `hold_file_count integer null`.
- Foreign keys to ingestion and section records.
- Checks require all present counts to be nonnegative.

An index on `(semester_code, section_id, ingestion_id)` supports section history. Observation timestamps come from the referenced ingestion.

Observations are authoritative. They are never updated after insertion.

#### `seat_events`

- `id uuid primary key`, supplied by the application.
- `semester_code text not null` and `department_code text not null`.
- `course_id text not null`, `section_id text not null`, and `section_number text not null`.
- `event_type text not null`, constrained to every event emitted by `compareDepartmentSnapshots`: `SEATS_OPENED`, `SECTION_FILLED`, `OPEN_SEATS_CHANGED`, `TOTAL_SEATS_CHANGED`, `WAITLIST_CHANGED`, `HOLD_FILE_CHANGED`, `SECTION_ADDED`, and `SECTION_REMOVED`.
- `previous_ingestion_id uuid not null` and `current_ingestion_id uuid not null`.
- `previous_value jsonb null` and `current_value jsonb null`.
- `delta integer null`.
- `created_at timestamptz not null default now()`.
- Foreign keys to both ingestion records and the section record.
- Unique constraint on `(current_ingestion_id, section_id, event_type)`.

JSONB values preserve the existing comparison union: count events store JSON numbers or null, while addition/removal events store the complete seat-count object or null. Event type, section identity, ingestion provenance, and delta remain directly indexable.

Indexes support events by section/time, type/time, and current ingestion. Events are a query-optimized derivative and can be rebuilt from immutable snapshots and observations.

## Ingestion Architecture

Fetching and parsing remain independent from persistence.

- Existing `npm run scrape -- --semester <semester> --department <department>` continues to fetch, parse, and atomically write a JSON snapshot.
- New `npm run ingest:db -- --semester <semester> --department <department>` reuses the same fetch and parse functions but passes the in-memory `DepartmentSnapshot` directly to PostgreSQL persistence.
- Database ingestion never writes or rereads a JSON file.
- A database failure cannot change the existing JSON scraper's behavior.

The code is divided into four responsibilities:

1. The existing Testudo fetch/parser builds a `DepartmentSnapshot`.
2. A database connection module validates `DATABASE_URL`, creates the `pg` pool, wraps it with Drizzle, and exposes explicit shutdown for CLI use.
3. A snapshot repository performs transactional persistence and returns an ingestion result.
4. The database CLI validates arguments, runs fetch/parse plus persistence, prints a concise result, maps argument errors to exit code 2, and maps fetch, parse, configuration, migration, or persistence failures to exit code 1.

## Transaction and Idempotency

Persistence rejects `partial` snapshots before starting database writes.

For a complete snapshot, one Drizzle transaction performs these steps:

1. Upsert the semester and department reference rows.
2. Insert the corresponding ingestion-head row if missing, then lock it for update. This serializes ingestion for one semester/department while allowing unrelated departments to ingest concurrently.
3. Look up the unique `(semester, department, collected_at)` ingestion key.
4. If it exists and its stored snapshot JSONB equals the provided snapshot, return its ID with `alreadyPersisted: true` without creating data.
5. If the key exists with different snapshot content, fail as an idempotency collision.
6. Reject the snapshot if its collection time is not later than the current head. Historical backfill is out of scope.
7. Load the exact previous complete snapshot JSONB referenced by the head, if present.
8. Insert the immutable ingestion row.
9. Upsert all courses and sections in the snapshot as active, update their current metadata and last-seen ingestion, and replace their ordered child rows.
10. Mark previously active courses and sections in the same semester/department that are absent from this complete snapshot inactive. No historical row is deleted.
11. Insert one immutable seat observation for every section present in the new snapshot.
12. If a previous ingestion exists, call the existing `compareDepartmentSnapshots` function and insert every returned event with the previous and current ingestion IDs. The first ingestion creates no events.
13. Update the ingestion head to the new ingestion and collection time.
14. Commit.

Any exception rolls back the ingestion, normalized updates, observations, events, and head change together.

The database constraints provide a second idempotency layer. Retrying the exact same snapshot cannot create duplicate ingestion, observation, or event rows.

## Connection Lifecycle and Migrations

The application connection module accepts an explicit connection string for tests but defaults to `process.env.DATABASE_URL`. Missing or blank configuration produces a typed error without echoing credentials.

CLI execution creates one pool, passes the Drizzle database handle into persistence, and closes the pool in a `finally` block. Application code does not create global connections during module import, keeping tests and future web-server lifecycle management predictable.

`drizzle.config.ts` reads `DATABASE_URL`, points to the TypeScript schema, selects the PostgreSQL dialect, and writes generated migrations under `drizzle/`.

Package scripts include:

- `db:up` and `db:down` for Docker Compose.
- `db:generate` for migration generation.
- `db:migrate` for explicit migration application.
- `db:studio` for optional local inspection.
- `ingest:db` for PostgreSQL-backed Testudo ingestion.
- `test:db` for opt-in PostgreSQL integration tests.

Migrations never run automatically on application startup or ingestion.

## Error Handling

The database layer uses typed errors for:

- Missing or invalid database configuration.
- Partial snapshot rejection.
- Idempotency collisions.
- Out-of-order snapshots.
- Persistence failures whose safe public message omits credentials and query parameters.

The CLI prints a concise error to stderr and exits nonzero. Drizzle and PostgreSQL errors may be retained as error causes for logs and tests but are not interpolated into user-facing messages when they could contain connection details.

## Testing Strategy

### Offline suite

The normal `npm test` suite does not require Docker or PostgreSQL. It covers:

- Database environment validation.
- Mapping the full snapshot model to normalized rows.
- Complete-versus-partial validation.
- Event conversion for every current comparison event shape.
- CLI argument handling, connection cleanup, success output, and safe failure output.
- Transaction orchestration through a narrow repository boundary where a real database is not necessary.

### PostgreSQL integration suite

`npm run test:db` requires `TEST_DATABASE_URL`. Before applying migrations or clearing tables, its safety guard parses the URL and requires the database name to end in `_test`.

The suite uses the real Drizzle schema, generated migrations, and PostgreSQL constraints. It runs serially and resets only the guarded test database. It verifies:

- Initial migrations and constraints.
- First ingestion as a baseline with observations and no events.
- A later ingestion with objective count events.
- Section additions and removals.
- Current catalog upserts and inactive records.
- Ordered requirement, instructor, and meeting replacement.
- Exact retry idempotency.
- Same-key/different-content collision rejection.
- Partial snapshot rejection.
- Out-of-order rejection.
- Rollback when persistence fails after intermediate writes.
- Explicit previous/current ingestion provenance on every event.

Existing fetch/parser live tests remain separate from database tests so failures identify the correct boundary.

## Acceptance Criteria

- Local PostgreSQL starts from committed Compose configuration plus an uncommitted `.env`.
- No real credential is committed or hard-coded.
- The initial migration builds the documented schema on an empty PostgreSQL database.
- Existing JSON scraping behavior and tests are unchanged.
- `ingest:db` persists a complete CMSC 202608 snapshot directly from memory.
- The first ingestion creates normalized catalog records and observations without events.
- A later ingestion creates only the objective comparison events and records both ingestion IDs.
- Retrying the same snapshot is a no-op that returns the original ingestion ID.
- Partial, conflicting, out-of-order, or failed ingestion leaves no partial database state.
- Offline and PostgreSQL integration suites pass.
